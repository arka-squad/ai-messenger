## [high] Feedback (c): -app and -channel expose the same 15 tools under separate identities, the guidance contradicts itself, and wake-up only reaches the channel identity

`duplicate-app-and-channel-tool-servers` · agent-tools · vérifié

- **Avant :** There was one server per host, `arkalabs-messenger` (stdio, LEGACY mcp.py:174 serverInfo name). Identity was kept per host and folder (poste.py:65-75 resoudre_agent; mcp.py:455-458 _adopter writes memoriser_identite). Wake-up came from hooks and the watch, not from a second tool server (CONSIGNES mcp.py:49-51).
- **Maintenant :** Claude equip registers both servers: `arkalabs-messenger-app` over HTTP and `claude mcp add --scope user arkalabs-messenger-channel` (provider/claude.rs:36, 199); ~/.claude.json has both entries. The channel's tools/list returns `mcp::channel_tools()`, which is `tools()` (claude.rs:333-334; mcp.rs:199-201), and its calls are dispatched as another session (claude.rs:336-344, using the random UUID from claude-channel.ts:20). Identities are keyed `session:{provider}:{session}` (directory.rs:125-140), so an m_enroler on the second server creates a second account with a numeric suffix (directory.rs:202-218), and every envoyer gets a fresh id (mcp.rs:258), so both servers can send. The invite says "n’appelle pas les mêmes outils par arkalabs-messenger-channel" (owner_commands.rs:110), while the channel instructions say "Enrôle cette session avec m_enroler ... Utilise les outils Messenger pour relever, lire, répondre" (claude-channel.ts:35-37). An agent that follows the invite and uses -app only gets Reachability::NoSession (delivery.rs:48-53).
- **Impact :** Agents see each tool twice. Using -channel duplicates the account, and therefore the mail and the actions. Using only -app, as the invite says, means the agent is never woken when mail arrives. The two choices fail in opposite ways, and nothing in the tool list says which server to use.
- **Correctif proposé :** Simpler than a binding tool: use one server per host. For Claude Code, when the sidecar exists, register only the stdio -channel and make it the tool server. Its per-process UUID is stable for the whole session and survives app restarts, and wake-up then works with no extra step. Add process.cwd() to its register frame to get a resume key per folder. Keep -app over HTTP for Codex and Kimi. Align the invite and claude-channel.ts instructions. If both must stay, at least make channel_tools() return an empty list.
- **Vérification :** NEW: equip registers both `arkalabs-messenger-app` over HTTP (claude_http.rs:24-36) and `arkalabs-messenger-channel` (claude.rs:36, 199). ~/.claude.json on this PC has both entries. channel_tools() returns tools() (mcp.rs:199-201; claude.rs:333-334). Channel calls run as another session with live_session:true (claude.rs:336-344). account_route is written only when live_session is true or an explicit delivery_session is passed (mcp.rs:225-228). The hub delivers only to registered channel UUIDs (claude.rs:114-126), and otherwise returns NoSession (delivery.rs:48-53). The invite (owner_commands.rs:110) says to avoid -channel, while the channel instructions (claude-channel.ts:35-37) say to enrol through it. ADDED PRECISION: in this Windows session the -channel server's instructions are loaded but none of its tools are listed, only the -app tools. rpc() awaits connect() before arming its 30 s timer, and connect() loops forever while the app is down (claude-channel.ts:49-58, 70-80), so tool listing through the channel is also unreliable. Channel push also requires a session launched with channels enabled (claude.rs:436 "limité aux sessions qui l’ont activé"). LEGACY: a single stdio server per host (mcp.py:174), with wake-up from hooks and watch (mcp.py:49-51, cli.py:503-528).

## [high] Feedback (b): write tools take untyped objects, decode errors drop the faulty field, and refusals are not flagged as errors

`opaque-schemas-and-unhelpful-refusals` · agent-tools · vérifié

- **Avant :** Schemas were flat and typed, with descriptions (mcp.py:218-290), for example send {to: array of string, subject, body: string "At most two lines", attach, reply_to} and mark {id, status enum [lu, traité]}. _valider names the field: `required argument: {requis}`, `"{cle}": expected {type}`, `expected one of ...` (mcp.py:481-501). A body string is split into lines (messagerie.py:254, corps.splitlines()). Domain refusals return isError: True (mcp.py:207-208; PROTOCOLE.md:181-182: "Domain rejections are returned as tool results with isError"). An unknown recipient is named: "recipient(s) without an active account: X — active accounts: … — your address book: …" (modele.py:586-588).
- **Maintenant :** Declared schemas: envoyer/repondre `"message":{"type":"object"}`, marquer `"marking":{"type":"object"}`, demander_* `"request":{"type":"object"}`, cloturer `"closure":{"type":"object"}`, contacts `{"type":"array"}` (mcp.rs:187-195). Hidden required fields: MailMessage.to, subject and body: Vec<String> (models.rs:65-78); Marking.message_id and status "lu"|"traité" (models.rs:80-95); ApprovalRequest gesture, scope, reversible, if_refused, why_now (models.rs:106-118), which no agent-visible text documents; RequestClosure request_id and result (models.rs:151-158); Contact.note, required with no default (journal.rs:24-29). decode() discards the serde error: "argument_invalide", "Les arguments ne respectent pas le contrat de l’outil." (mcp.rs:346-352). Refusals go through tool_result with no isError (mcp.rs:328-335), and the SDK test asserts `!result.isError` and then reads `.refus.reason == 'NotRecipient'` (scripts/test-mcp-http.mjs:16,34). Domain errors surface Rust Debug names with English text (mcp.rs:333-334; domain.rs:231-249). For an unknown recipient the reply is "Ce compte n’existe pas dans cette boîte. Enrôle-toi ou reprends ton compte." (directory.rs:106-111, called for each `to` at mailbox.rs:147-149); it neither names the address nor lists the valid accounts.
- **Impact :** Agents have to guess field names by trial and error. A string body (the legacy shape) fails with no hint. A demande_validation cannot be built without reading the Rust source. Hosts show refused sends and marks as successful calls, so agents can believe a message left when it did not. A typo in a recipient is reported as if the sender were not enrolled.
- **Correctif proposé :** Highest return: (1) Full nested JSON Schemas with descriptions and enums in tools(), especially for demander_validation's five fields. (2) serde_path_to_error in decode(), returning the path. (3) Accept body as a string and split it on lines; add #[serde(default)] to Contact.note. (4) In MailboxService::send, name the unknown addresses. (5) For isError, confirm with the owner that it does not conflict with SPEC §6; at least prefix the text content with "REFUS <reason> : <message>" so the host renders it visibly.
- **Vérification :** NEW: mcp.rs:187-195 declares message, marking, request and closure as bare {"type":"object"} and contacts as an untyped array. Hidden required fields: models.rs:66-78 (to, subject, body: Vec<String>); models.rs:81-87 (message_id, status "lu"|"traité"); models.rs:107-118 (gesture, scope, reversible, if_refused, why_now, which appear in no agent-visible text); models.rs:152-158; journal.rs:25-29 (note, required, no default). decode() discards the serde error (mcp.rs:346-352). tool_result never sets isError for refusals (mcp.rs:328-335, 370-376), and scripts/test-mcp-http.mjs:16,35 relies on that. Domain refusals come back as Rust Debug names with English text (mcp.rs:333-334; domain.rs:231-249). An unknown recipient gets the sender's message "Ce compte n’existe pas dans cette boîte. Enrôle-toi ou reprends ton compte." (directory.rs:106-111, via mailbox.rs:147-149). LEGACY: typed flat schemas with descriptions (mcp.py:216-291). _valider names the field (mcp.py:481-501). Refusals are isError:true (mcp.py:207-208). The unknown recipient is named with the active accounts and the address book (modele.py:582-588). A body string is split into lines (messagerie.py:254). PRECISION: refusals without isError follow a deliberate spec choice, SPEC-messenger-20260921.md:285-289 ("un refus gouverné est une donnée … pas une erreur"). MCP isError is still a tool result, not a JSON-RPC error, so setting it is compatible, but it is the owner's call.

## [high] relever and attendre no longer mean "new mail": attendre returns at once with the same backlog, is capped at 5 minutes, and nothing can wait between turns

`relever-attendre-new-mail-semantics-lost` · agent-tools · vérifié

- **Avant :** `check` returns only mail still `nouveau` for me (mcp.py:248-249, 322-324; messagerie.py:265-271). `wait` snapshots the pending ids at start and returns only mail that arrives afterwards (`deja = {m.id for m in messagerie.releve(moi)}` ... `recus = [m ... if m.id not in deja]`, mcp.py:383-396). It returns `received: []` on timeout, allows up to 3600 s (mcp.py:38) and is cancellable (mcp.py:160-164). Each summary carries `status` as seen by me (mcp.py:462-465), and read adds `addressed_to_me` and `next_status` (mcp.py:338-342). For waiting between turns, CONSIGNES says to run `messenger.py watch ... It wakes your session when mail arrives. Restart it after every wake-up` (mcp.py:49-51; cli.py:503-528).
- **Maintenant :** inbox() keeps every message addressed to me that is not `traité`, including `lu`, plus every copy forever: `if (addressed && !done) || copy` (mailbox.rs:277-301). Copies can never be marked, so they never leave. await_mail returns immediately whenever that list is not empty (receive.rs:302-305). The attendre handler ignores what it returns and sends back the whole inbox (mcp.rs:324). The maximum is 300 s (mcp.rs:196; receive.rs:296). MessageView has no "my status" field, only a `statuses` map keyed by address (views.rs:4-17). The new app has no CLI, watch or background waker, and INSTRUCTIONS (mcp.rs:24) only says "relève à l’ouverture et lorsque ton humain te parle". No test covers attendre semantics (grep finds none).
- **Impact :** Once an agent has a single message marked `lu` but not `traité`, or has ever been in copy, attendre returns at once with the same messages. A wait loop then spins, or the agent reads "nothing new" into the backlog and misses real arrivals. relever re-announces old copies on every call. Outside a turn, nothing wakes Codex or Kimi agents, or Claude agents without the channel (see the duplicate-tool-servers finding).
- **Correctif proposé :** In await_mail, snapshot inbox ids before the loop and return only new ids. Have attendre return {received:[…]}, with an empty list meaning timeout, and raise the cap. In relever, keep the spec's 'not traité' for addressed mail, but show a copy only until the account's first Collected event after it arrived. Add `mon_statut` to the views returned to agents. For automation, consider shipping a tiny Claude/Codex SessionStart+UserPromptSubmit hook that queries the local app. This is the cheapest way to restore legacy's automatic 'MAIL —' notices.
- **Vérification :** NEW: inbox() = `(addressed && !done) || copy` (mailbox.rs:277-301), so copies are returned forever and can never be marked (mailbox.rs:218). await_mail returns at once whenever inbox is non-empty (receive.rs:301-305). attendre ignores its result and returns the whole inbox (mcp.rs:324). The cap is 300 s (mcp.rs:196; receive.rs:296). MessageView has no per-caller status (views.rs:4-17). No CLI, watch or hook exists, and INSTRUCTIONS only say "relève à l’ouverture et lorsque ton humain te parle" (mcp.rs:24). CORRECTION: returning `lu`-but-not-`traité` mail from relever follows the spec (SPEC-messenger-20260921.md:278 "ce qui m'est adressé et que je n'ai pas traité"), so it is not a regression to undo. attendre's behaviour does contradict the spec (SPEC:288 "bloquer jusqu'au prochain message qui m'est adressé"). Wake-up is narrower than claimed, not absent: Codex can be queued through `codex queue --thread` when the agent gave delivery_session (codex.rs:51-59, 130-131). Kimi gets nothing (kimi.rs:99-100). LEGACY: wait snapshots and returns only new ids (mcp.py:383-396), with max 3600 s (mcp.py:38) and cancellation (mcp.py:160-164). The watch waker exists (cli.py:503-528). Biggest loss, not listed in any candidate: the hooks injected 'MAIL — …' into context at SessionStart/UserPromptSubmit and blocked Stop while mail was pending (cli.py:438-481; hotes.py:44-48). The new app has no equivalent automation.

## [high] Agent identity is tied to a throwaway in-memory MCP session: any app restart, rebuild, change of box, reconnection or new/resumed agent session silently removes it

`identity-lost-on-mcp-reconnect` · identity · vérifié

- **Avant :** Identity was remembered on disk per host + repository and resolved automatically. poste.py:65-74 resoudre_agent: "`--agent`, sinon MESSENGER_AGENT, sinon l'agent de cette session, sinon le dernier enrôlé ici"; poste.py:87-100 identite_memorisee(hote, dossier) walks up to the repository root; mcp.py:455-458 _adopter -> poste.memoriser_identite. AGENTS.md:58-59: "It remembers the identity per host and repository on that machine." On this PC, ~/.arkalabs-messenger.json still holds 4 'identites' entries such as "claude-code|...\arkalabs-messenger": "cl-agent-messengerai-win@ai-messenger". Restarting the UI had no effect on agents because each stdio MCP server was owned by its own session (mcp.py:1-12).
- **Maintenant :** mcp.rs:100-115 generates `let session = new_id();` on every `initialize` and keeps the transport->session map only in memory (mcp.rs:33-34, 51). An unknown mcp-session-id gets a 404 (mcp.rs:128-130), so the client re-initializes and receives a new session. directory.rs:125-131 looks identity up under `session:{provider}:{session}`, so the new session is unknown and every tool then refuses (mcp.rs:231: "session_non_enrolee"). The app restarts itself after a box change (lib.rs:105 and lib.rs:120, `app.request_restart()`), and each box has its own local database that holds the session bindings and recovery hashes (lib.rs:349-357 store_path). Seen live during this audit: qui_suis_je first returned account "messenger-tauri-1@messenger" on installation c614654a…; the host then reported arkalabs-messenger-app disconnected and reconnecting; ou_en_est then returned {"refus":{"reason":"session_non_enrolee"}}; qui_suis_je then returned {"identity":null, "installation":"51930bc6…"}. The installation changed too, so the recovery key of that account no longer matches anything on the running app.
- **Impact :** After every restart or update of the app, and in every new or resumed Claude, Codex or Kimi session, agents lose their address without being told. Their tools refuse to work, they stop collecting their mail, and messages addressed to them go unseen. This matches the user's report that an agent sent a message and nothing was seen. Getting the identity back depends on the agent having kept its key (see the recovery-key finding). If the installation changed, the key no longer works at all.
- **Correctif proposé :** The proposed `roots/list` fix is heavy: this server only answers POST with JSON and has no SSE stream for server-to-client requests (mcp.rs:47-48). Minimal fix in two steps. (1) Stop orphaning clients on restart: on initialize, persist `mcp_transport:{transport}` = {provider, session} with set_setting. In handle(), when the id is not in memory, look it up in the store instead of returning 404. A Claude, Codex or Kimi session then keeps its identity across app restarts and updates. (2) For a new session, add an optional `dossier` argument (the agent's cwd) to qui_suis_je, m_enroler and me_reconnaitre. Store `identity:{provider}:{realpath(dossier)}` -> account, as legacy poste.memoriser_identite did. In qui_suis_je, rebind automatically, or at least return the candidate. For Claude, have the channel sidecar send `process.cwd()` in its register frame (claude-channel.ts:91), so the same key works with no action from the agent.
- **Vérification :** NEW: mcp.rs:108-114 `let transport = new_id(); let session = new_id();` kept only in the in-memory map (mcp.rs:34,51). An unknown mcp-session-id returns 404 at mcp.rs:128-130, so the client re-initializes and gets a fresh session. Identity is looked up only under `session:{provider}:{session}` (directory.rs:125-131), and every other tool then refuses with `session_non_enrolee` (mcp.rs:231). lib.rs:105 and lib.rs:120 call `app.request_restart()` after a box change. Each box opens its own store (lib.rs:349-357, 379-381), and that store holds both the `session:*` bindings and the `recovery:*` hashes. On this PC, %APPDATA%/app.arkalabs.messenger/installation-id was created 2026-10-01 10:41, and exchange-location (now the HTTPS box) at 13:13 with a new boxes/45e5…/database, so the earlier bindings stay in the other box's database. LEGACY, correcting the claim: the stdio MCP server did NOT auto-adopt the remembered identity. mcp.py:511 calls `poste.resoudre_agent(agent)` without host or folder, so only --agent or MESSENGER_AGENT counted. However, whoami (mcp.py:295-301) named the remembered identity ("last identity used here: {connue}; call `identify`"), and identify needed no secret (messagerie.py:182-204). The hooks resolved identity on their own from session_id or host+folder (cli.py:412-422 `poste.resoudre_agent(args.agent, session, args.host, dossier)`), so MAIL notices kept arriving with no action from the agent. Precision on the NEW side: the Claude channel uses one UUID per sidecar process (claude-channel.ts:20) and re-registers with the same UUID after an app restart (claude-channel.ts:91, 127-137). Its `session:claude-code:<uuid>` binding therefore survives an app restart. Only the HTTP -app path loses identity on restart; both paths lose it in a new agent session or after a box change. The link to the user's 'tu n'as rien vu' is plausible, not proven.

## [high] m_enroler in a new session with the same task creates a new suffixed account (-1, -2…) instead of returning the agent's existing account

`re-enrolment-creates-duplicate-account` · identity · vérifié

- **Avant :** Enrolment was idempotent per host + task + machine. messagerie.py:161-176 enroler: "Le même agent qui revient (même machine) retrouve son compte ; un homonyme d'une autre machine reçoit un suffixe". modele.py:520-532 nom_libre returns the existing account when `existant.machine == machine`. A test proves it: tests/test_enrolement.py:76-80 "ré-enrôlement de la même machine → on réutilise le même compte" / assertIn("already enrolled"). The guidance promised it: disposition.py:122 "Using the same task name in a later session returns the same account." The shared box onboarding.md says "Si tu reviens dans une nouvelle session, le même intitulé te rend le même compte."
- **Maintenant :** directory.rs:190-192 recognizes an earlier enrolment only for the same provider+session (`already_enrolled`). Otherwise directory.rs:202-218 loops `format!("{prefix}-{suffix}")` until the address is free and publishes a brand-new Account, even on the same installation and for the same provider and task. No test covers re-enrolment (mcp_tests.rs:177 enrols only once). Precision on agent feedback (c): the Claude channel runs its own session (claude-channel.ts:20 `const session = randomUUID()`), and its server instructions say "Enrôle cette session avec m_enroler" (claude-channel.ts:37), while the invitation says "n’appelle pas les mêmes outils par arkalabs-messenger-channel" (owner_commands.rs:110). An agent that follows the channel enrols a second time and gets a second account.
- **Impact :** Combined with the reconnection finding, each app restart or new agent session can produce one more account for the same agent (cl-agent-x-win, then -1, then -2…). The display name stays the same, so the human sees look-alike duplicates. Mail sent to the original address waits unread in an account nobody holds any more, and the directory and contact lists fill with dead accounts that can only be cleaned up by hand-merging.
- **Correctif proposé :** The proposed fix is right and minimal. In enroll_as, before the suffix loop: if an active account with the derived address has installation == self.installation and host == provider, bind this session to it. Do not mint a new key, return the existing one-time state with already_enrolled:true, and refresh account_route when delivery_session or the channel is present. Suffix only for other installations. Compare machine case-insensitively for legacy accounts, which stored 'GrimWorkshop' while the new app uses 'GRIMWORKSHOP'. Add the missing test: enrol, new session, enrol with the same tache, same address.
- **Vérification :** NEW: directory.rs:190-192 returns already_enrolled only when this exact provider+session already has an identity. Otherwise directory.rs:202-218 loops `format!("{prefix}-{suffix}")` whenever the address exists, with no check on installation, machine or provider, then publishes a new Account (directory.rs:245-248) and a new key (directory.rs:239-244). ## [medium] relever and attendre are no longer a cheap read-only check: each call writes to the shared journal, holds the write lock, and its cost grows as messages × journal size

- **Maintenant :** relever = `receive()` + `event(Collected)` + `inbox_views` (mcp.rs:236), so every check publishes a new shared event. receive() holds the `sync` and `changes` locks (receive.rs:5-6) while it lists the box, reads and SHA-256-hashes every attachment (receive.rs:15-26), rebuilds message_views, which hashes every attachment again (views.rs:188-198), and writes a checkpoint (receive.rs:261-273). inbox() (mailbox.rs:277-300) calls is_recipient, is_copy and resolve_account for each message and each recipient. Every event includes the Collected entries that relever itself adds. The poller repeats receive, deliver and notify every 10 s on the remote box (lib.rs:408-427; remote listen is unsupported, remote_exchange.rs:159-161). The dev report measured 349 ms for one indexed query on the real prototype box (outputs/CR-DEV-MSG-perimetre_complet-20260927-01.md:153). - **Correctif proposé :** Load accounts() and the resolve map once per call and pass them down to inbox(), is_recipient() and statuses().
